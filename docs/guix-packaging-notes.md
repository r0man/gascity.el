# Guix packaging notes: does `gascity-next` cause the rig-setup friction?

> Research bead `gce-ksf`. Investigates whether the recurring gascity rig-setup
> friction is caused by how the `gc` CLI is packaged/run on Guix via the
> `gascity-next` package in `~/workspace/guix-channel`.

## TL;DR

**Mostly no.** Of the three friction points, only **#1 (vanishing
`.gc/system/packs/` edits)** is rooted in the Guix model — and even there the
root cause is a *by-design reconciler behavior*, with Guix only sharpening it by
making the binary immutable. The other two are gascity-side issues independent
of packaging:

| 1 | Files written to `.gc/system/packs/**` vanish in seconds | **By-design** reconciler prune; *amplified* by Guix immutability | No — working as intended. Durable changes go via overlay dirs or the channel |

## How `gascity-next` is packaged

`gascity-next` is a `go-build-system` package that builds the `gc` CLI from
`github.com/gastownhall/gascity` (`cmd/gc`) at a pinned commit
(`task-management.scm:416-424`). It installs:

- `bin/gc` — the single Go binary.
- `etc/bash_completion.d/`, `share/{zsh,fish}/…` — shell completions generated by running `gc completion …` at build time (`task-management.scm:448-467`).
- `share/gascity/examples/{bd,dolt,gastown}` — the upstream `examples/` tree, each example city carrying its own `packs/` subtree, used by `gc init --from <out>/share/gascity/examples/<name>` (`task-management.scm:468-480`).
- Propagated runtime deps: `beads-next` (the `bd` CLI), `dolt`, `jq`, `lsof`, `procps`, `tmux`, `util-linux` (`task-management.scm:515-521`).

**Key fact for everything below:** the *system packs* the runtime uses are **not**
read from `share/gascity/examples/` at run time. They are **embedded inside the
`gc` binary** via Go `embed` (`internal/builtinpacks`) and re-materialized to disk
on demand. The `examples/` tree is only a seed for `gc init --from`.

## Friction #1 — edits to `.gc/system/packs/**` vanish within seconds

**Confirmed, and the operator's hypothesis is correct in spirit but wrong in
mechanism.** The packs are not "installed from the immutable Guix store" at
run time; they are **embedded in the `gc` binary** and **re-materialized + pruned
by the supervisor on every reconcile cycle.**

Mechanism (`cmd/gc/embed_builtin_packs.go`):

- `builtinPacks = builtinpacks.All()` — the embedded packs (`core`, `gastown`, `dolt`, `bd`, `maintenance`), baked into the binary at build time (`:25-27`).
- `MaterializeBuiltinPacks(cityPath)` (`:54-69`) writes each embedded pack to
  `<city>/.gc/system/packs/<name>/` (`SystemPacksRoot = ".gc/system/packs"`,
  `internal/citylayout/layout.go:28`), then calls…
- `pruneStaleGeneratedPackFiles(dst, desired)` (`:388-446`) which walks the
  destination and **`os.Remove`s any file not in the embedded manifest** (`:419`).

This is the "vanishing": any file you add under `.gc/system/packs/<name>/` is
not in `desired`, so it is deleted on the next materialize. The function header
states it plainly: *"Idempotent: safe to call on every gc start and gc init"*
(`:53`).

`MaterializeBuiltinPacks` runs on the config-load path (`embed_builtin_packs.go:124`),
on init-provider readiness (`init_provider_readiness.go:42`), and on the
supervisor reconcile loop — so on this town it fires roughly every
`daemon.patrol_interval`, which `city.toml` sets to **`30s`**. That matches the
"vanish within seconds" observation.

**Classification: by-design, amplified by Guix.** The prune would happen on any
install — it is how the runtime keeps system packs in sync with the binary.
Guix only adds that you cannot patch the binary in place (it is a read-only store
output), so the *binary-embedded* content is doubly immutable. This is correct
behavior, not a bug.

**Durable fix surface:** see ["Making durable changes"](#making-durable-changes-on-a-guix-managed-town).
To change the *content of a system pack itself* (e.g. the `gastown` pack), the
only path is upstream: edit `internal/builtinpacks` in `gastownhall/gascity`,
land a commit, bump `task-management.scm` to that revision, and
`guix pull` / `guix home reconfigure`. Local edits under `.gc/system/packs/` are
futile by design.

## Friction #2 — `gc rig add --include packs/gastown` wrote a broken `source`

**Could not reproduce on the installed revision** — and the root cause is an
**operator input error**, not a Guix artifact. The live town config is *correct*:

```toml
# /home/roman/bright-lights/city.toml  and  pack.toml
[rigs.imports.gastown]
source = ".gc/system/packs/gastown"     # ← correct, resolvable
```

What actually happened is explained by `legacyImportSourceFor`
(`internal/config/config.go:774-790`):

```go
func legacyImportSourceFor(include string, packs map[string]PackSource) string {
    include = strings.TrimSpace(include)
    if spec, ok := packs[include]; ok {          // include IS a known pack name
        return spec.Source                        // → ".gc/system/packs/gastown"  ✓
    }
    if looksLikeLegacyLocalImportPath(include) &&  // looks like a path…
        !strings.HasPrefix(include, "./") && … {
        return "./" + include                      // → "./packs/gastown"          ✗
    }
    return include
}
```

`looksLikeLegacyLocalImportPath` (`:854-862`) returns true for essentially any
token that is not a URL. So:

- `gc rig add --include gastown` → `gastown` is a registered pack name (the town's
  `pack.toml` declares `[defaults.rig.imports.gastown]`), so the first branch
  returns the canonical `.gc/system/packs/gastown`. **This is the correct usage,
  and it is what produced the live config.**
- `gc rig add --include packs/gastown` → `packs/gastown` is *not* a pack name, it
  *looks* like a relative path, so `./` is prepended → `./packs/gastown`, which
  later resolves against the city root to the nonexistent `<city>/packs/gastown`
  (resolution in `internal/config/compose.go`, `resolveConfigPath`).

So the operator passed the **on-disk subpath** (`packs/gastown`) where the CLI
expects the **pack binding name** (`gastown`).

**Classification: operator input error + a gascity CLI sharp-edge.** The genuine
gascity-side defect is that `gc rig add --include` *silently accepts* an unknown
token, treats it as a local path, and writes an unresolvable `source` with **no
validation** that the path exists. It is unrelated to Guix.

**Already partly addressed:** CHANGELOG (`CHANGELOG.md:131-132`) records *"`gc rig
add --include` now writes canonical `rig.Imports`…"* — the rework that makes the
correct (`--include gastown`) form emit `.gc/system/packs/gastown` as seen live.

**Fix surface (upstream gascity, optional hardening):** in
`legacyImportSourceFor` / the `gc rig add --include` handler, reject or warn when
an include token is neither a known pack name nor an existing/ resolvable path,
instead of blindly prepending `./`. Until then, the operator workaround is simply
to **use the pack binding name** (`--include gastown`), not the subpath.

## Friction #3 — `bd init`/bootstrap schema missing the 13 custom types

**Confirmed as a real gap, but it is by-design two-tier bootstrap, not a Guix
artifact — and it is already remediated on this town.**

`bd` (from `beads-next`) is a generic, gascity-agnostic issue tracker; `bd init`
creates a vanilla schema (`task`, `bug`, `epic`, …). The 13 gastown types are a
*gascity* concept and are layered on afterward. They are defined as a Go slice in
`internal/doctor/checks_custom_types.go:25-29`:

```go
var RequiredCustomTypes = []string{
    "molecule", "convoy", "message", "event", "gate",
    "merge-request", "agent", "role", "rig", "session", "spec",
    "convergence", "step",
}
```

Registration is performed by **`gc doctor --fix`**, whose `CustomTypesCheck.Fix`
merges the required set into the store via `bd config set types.custom <list>`
(same file). There is **no `.sql`/`.toml` schema file** — the types live only in
that Go slice, so a plain `bd init`/`bootstrap` cannot know about them.

Verified on the live town — both stores already carry the full set:

```
$ bd config get types.custom        # city store AND gascity.el rig store
molecule,convoy,message,event,gate,merge-request,agent,role,rig,session,spec,convergence,step
```

So `gc doctor --fix` (or an init path that calls the same check) has already run
here; agents work because the types are present.

**Classification: by-design two-tier bootstrap; gascity UX gap.** The friction is
that the custom-type registration is a *separate* step from `bd init` and is easy
to miss if you bootstrap beads by hand. The CHANGELOG points the same direction:
`gc import migrate` is now a deprecated shim that *"points operators to `gc doctor`
and `gc doctor --fix`"* (`CHANGELOG.md:127-130`).

**Fix surface / recommendation:** never hand-run bare `bd init` for a gascity
store and expect it to be complete. Run **`gc doctor --fix`** after any
init/bootstrap (it checks the city store and every rig store). If repeated
manual setup is needed, the durable answer is to ensure the init path invokes the
custom-types check — but for operators the one-liner `gc doctor --fix` restores
the schema.

## Making durable changes on a Guix-managed town

The reconciler prune (`pruneStaleGeneratedPackFiles`) **only touches
`.gc/system/packs/<name>/`**. Everything outside that subtree is left alone.
That gives two tiers of durable customization:

### Tier 1 — no Guix rebuild needed (overlay surfaces)

These live *outside* `.gc/system/packs/` and survive every reconcile:

- **Custom orders** → `<cityRoot>/orders/*.toml` (`OrdersPath`,
  `internal/citylayout/layout.go:19,79`). City-level orders are discovered at
  highest priority and override pack-provided orders by name.
- **Custom formulas** → `<cityRoot>/formulas/…`; **custom agents** →
  `<cityRoot>/agents/…` (same overlay model).
- **Tweaks to system-pack orders** (enable/disable, change interval/schedule)
  without editing the managed files → `[[orders.overrides]]` in `city.toml`.
- **Rig-scoped orders** → `<rigRoot>/orders/*.toml`.

An order is a small TOML unit (`internal/orders/order.go`) with a `trigger`
(`cooldown`/`cron`/`condition`/`event`/`manual`) and either a `formula`
(dispatched to a `pool`) or an `exec` (shell command on the controller). Example
shape (from the upstream `maintenance` pack):

```toml
[order]
description = "…"
trigger = "cooldown"
interval = "1m"
exec = "gc order sweep-tracking --stale-after 10m --quiet"
```

So: **to add behavior, write an order/formula/agent in the city (or rig) overlay
dir — never under `.gc/system/packs/`.**

### Tier 2 — requires going through the Guix channel

To change the **content of a system pack itself** (`core`, `gastown`, `dolt`,
`bd`, `maintenance`) — because that content is compiled into the binary — the
durable path is:

1. Edit `internal/builtinpacks/…` in upstream `gastownhall/gascity`, land a commit.
2. Bump `gascity-next` in `task-management.scm` (`commit` + `revision`) to that commit and update the `sha256`.
3. `guix pull` then `guix home reconfigure` (this town uses `guix-home`; `gc` is provided via `~/.guix-home/profile`).

Local edits to `.gc/system/packs/` are non-durable by design and will be pruned.

## Is a newer `gascity-next` revision needed?

No. The channel `main` HEAD already pins **3494/f55bf85**, which is exactly the
binary installed and running. None of the three issues is blocked on a newer
revision:

- #1 is intended behavior at any revision.
- #2's canonical path is already correct at 3494 (live config proves it); the
  residual sharp-edge is a CLI hardening item, not a blocker.
- #3 is resolved operationally with `gc doctor --fix` (already applied here).

forward change to upstream gascity, after which the channel would bump as usual.
